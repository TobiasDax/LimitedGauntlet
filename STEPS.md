## Step 4 — Pairing engine ✅
- [x] `server/src/services/podStats.ts`: per-pod match points, opponent history, and bye history computed live from `Round`/`Match` rows (no separate stored-state table, per PLAN.md's design decision)
- [x] `server/src/services/weekendHistory.ts`: cross-pod, player-level "who's played whom this weekend" counts, resolving team entrants down to their member players so 2HG-style matches count every member of side A against every member of side B
- [x] `server/src/services/pairing.ts`: score-group sort (shuffled on round 1 for a genuine random draw, points-desc thereafter) + greedy pair-with-backtracking. Hard-avoid (within-pod repeat) is `Infinity` cost, so it's a true constraint; soft-avoid (repeat anywhere else this weekend) is a large-but-finite weight, so it degrades gracefully instead of failing when full avoidance becomes mathematically impossible
- [x] Bye handling: lowest score, no prior bye this pod, falls back to lowest score regardless if everyone's already had one
- [x] `server/src/routes/rounds.ts`: full round lifecycle — auto pairing (`POST /api/pods/:id/rounds`), manual pairing (`POST /api/pods/:id/rounds/manual`, validated so every active entrant appears exactly once and the bye count matches parity — no silent partial pairings), swap two entrant slots between pending matches (`POST /api/rounds/:id/swap`, rejects swapping a bye slot), start (locks further pairing edits, computes `endsAt` from `Pod.roundLengthMinutes`), result entry (`PATCH /api/matches/:id/result`, only while the round is ACTIVE), complete (blocked until every non-bye match has a result). Round-sequencing is enforced (`previous_round_not_completed`, `round_count_exceeded`) so pairing for round N always sees complete data for rounds 1..N-1
- [x] `GET /api/tournaments/:id/coverage`: weekend coverage matrix (player × player times-played), same underlying data the pairing soft-avoid uses
- [x] Found and fixed a real gap during live testing: `Entrant` creation didn't attach the player to `TournamentPlayer`, so someone actively playing in a pod could be invisible in the coverage view (and would have been in Gesamtwertung later) unless the organizer separately called the roster-attach endpoint. Fixed with `syncTournamentAttendance()` — upserted inside the same transaction as entrant/team creation, both branches (individual and team)
- [x] Verify — deterministic Vitest suite (`server/src/services/pairing.test.ts`) against a real throwaway Postgres, not mocks: (1) a full 8-entrant, 3-round pod never repeats an opponent, confirmed across 9 consecutive runs despite round-1's randomized draw; (2) bye assignment goes to a different entrant each round until everyone's had one; (3) given a completed Pod A where two pairs have already met, Pod B's fresh round-1 pairing for the same 4 players always avoids those pairs when an equally-valid alternative exists — this one is provably deterministic, not just probably-usually-true, because the crafted 4-player scenario has an all-zero-cost perfect matching that greedy-lowest-cost-first always finds before ever considering the higher-cost repeat option
- [x] Verify — full HTTP round-lifecycle exercised live against a running stack (not just the pure algorithm): 6-player pod through rounds 1-2 auto-paired with a verified zero repeat opponents between them, swap tested before lock and confirmed blocked after `start`, `complete` blocked until all results are in then succeeds once they are, manual pairing's validation confirmed rejecting both an incomplete roster and a wrong bye count, and cross-org 404s confirmed on round start / match result / coverage (three hops from org: round → pod → tournament → org)

### PI-11 — Inferred card-pull attribution (requested 2026-08-24, implemented same day, not yet deployed) ✅
Motivation: PI-7's "total value pulled" per-player stat is real infrastructure with no real data behind it — `CardPull.playerId` was never set by any UI, historical or otherwise. Tobias's proposed heuristic: a top-3 pod finisher almost always picked one of that pod's most valuable cards, above a real price floor. Auto-apply that as a *guess*, clearly marked, until a human confirms or reassigns it.
- [x] Schema: `CardPull.playerIdInferred Boolean @default(false)` (migration `20260824164024_add_card_pull_inferred_flag`). Sticky false once a human sets or confirms an attribution — inference never overwrites that.
- [x] `server/src/services/cardPullInference.ts`: `inferCardPullAttribution(podId)` — only runs once a pod is fully decided (every round played and `COMPLETED`), skips team pods entirely (a card can't be credited to "a team," only one player, and guessing which member would be worse than not guessing). Zips `computePodStandings()`'s top 3 ranks against the pod's card pulls sorted by price descending, **positionally** (rank *i* only matched against price-rank *i*, not "top 3 cards" as a shifted group) — so if the pod's 2nd-priciest card is under the €10 floor, the runner-up gets no guess at all rather than a wrong one. Threshold is a strict `> €10`, matching Tobias's own wording.
- [x] Wired into three triggers so it's genuinely automatic, not a manual button: adding a card pull (`POST /pods/:id/card-pulls`), completing a round (`POST /rounds/:id/complete`), and correcting a completed round's result (`PATCH /matches/:id/result`, from PI-5) — the last one matters because a score correction can change who finished top-3, and any *still-unconfirmed* guess should track that; a confirmed one never moves again regardless.
- [x] New `PATCH /api/card-pulls/:id` (`{playerId: string | null}`) — the same endpoint both confirms an inferred guess as-is (pass back the same playerId) and reassigns it to someone else; either way it clears `playerIdInferred`.
- [x] One-time backfill script `server/src/scripts/infer-existing-card-pulls.ts` (mirrors `import-legacy.ts`'s standalone-script pattern) — runs the same heuristic across every already-completed pod, for pulls logged before this feature existed. Idempotent, safe to re-run, never touches a human-set/confirmed pull. Run once after deploying: `docker compose exec app node server/dist/scripts/infer-existing-card-pulls.js`. **Not run against the real historical data in this session** — deliberately, since `legacy-data.local.json` holds real names the earlier privacy correction scrubbed from git history; Tobias runs this himself against the real deployment.
- [x] Frontend: `CardGallery` shows a 🔮 marker on any inferred, unconfirmed pull; on `PodValuePage` specifically (the only page with `editableAttribution` set) an inferred pull gets an inline `<select>` (defaulting to the current guess) + a one-click confirm button instead of just the marker. Confirmed/human-set pulls show a plain player name, no marker. New `useSetCardPullAttribution` hook.
- [x] Verify — live against a running compose stack, not just reasoning: built a real 4-player pod, added 4 pulls (two above €10, two below) in an order that didn't match finish order, played it out, and confirmed the top-2 finishers got matched to the top-2 priced cards *positionally* while the two sub-€10 pulls stayed unattributed. Confirmed one attribution via the PATCH endpoint, then corrected the completed round's result to flip the standings order, and confirmed the **confirmed** pull stayed put while the **unconfirmed** one updated to the new rank-2 player. Confirmed the backfill script is idempotent (0 pulls touched when everything's already attributed) and correctly re-infers a pull that's been manually cleared back to null. Screenshotted the `PodValuePage` UI showing a confirmed pull (plain name), an inferred pull (🔮 + select + confirm button), and pulls below the floor (no player shown at all).
