### PI-62 — Upload a photo of each entrant's drafted deck (v2 idea, scoped via interview 2026-08-31)
Idea from Tobias: on a pod's standings page, let each entrant have a photo of their drafted deck attached — flagged from the start as "more involved," scoped via an interview before any code. **This would be the app's first-ever user-uploaded file** — every prior "image" in the app (Scryfall card art) is a hotlinked external URL, never something stored by this app itself. `PLAN.md`/`CLAUDE.md` explicitly rule out file uploads for tournament descriptions (PI-31) as a deliberate scope boundary; this is the first place that boundary would be deliberately crossed.
- **Player self-upload now unblocked by PI-52:** PI-52 shipped the player auth surface (`requirePlayerAuth`, `/o/<slug>/player` portal). **Decided sequencing still holds:** ship v1 as **organizer-upload only**, then add a player self-upload path on top of `requirePlayerAuth` — same storage/display, just a second write route.
- **Scope:** any pod format (not draft-only — broader than PI-51's seating chart, which is draft-specific). One photo per entrant (a team pod gets one per team member, not one per team). No upload deadline/window — uploadable, replaceable, or addable anytime during the pod's life, even after it's complete.
- **Storage:** local disk / a new bind-mounted Docker volume, not an external object store — matches the app's existing minimal-moving-parts posture (single Dockerfile + Postgres, no Redis, no other required services). An S3-compatible backend was considered and explicitly declined in favor of this.
- **Keep original quality, but validate + sanitize (decided, refining the initial "resize down?" question):** store the uploaded file at original resolution/quality — but it must be verified as a genuine image (not an arbitrary file wearing a `.jpg` extension) before being accepted. The practical mechanism: decode it through a real image-processing library (e.g. `sharp`/libvips, a **new dependency** this app doesn't have yet) — reject anything that fails to decode as an image at all. Re-saving through that same decode step also strips embedded metadata/EXIF and any polyglot-file payload riding along with the pixel data, which is the standard mitigation for "accept an original-quality photo without accepting arbitrary attacker-controlled bytes." Whether the re-saved copy is byte-identical to the upload or just visually/resolution-identical is an implementation detail to settle when this is actually built, not a scope question.
- **Server-generated preview, not the raw original, for normal viewing:** on upload, also generate and store a smaller preview/thumbnail image (same new `sharp` dependency) — this is what's shown in-app. The full original stays available separately for two explicit actions: **zoom in** (view it at full resolution) and **download original**.
- **Visibility: public, same as the rest of the pod's standings** — no new public/private split. But **hidden by default, revealed on demand**: no thumbnail sits inline in the standings rows at all times. Each entrant gets a small button/link that opens a modal (reusing the shared `Modal` component already built for PI-45's share popup) showing their preview image, with zoom-in and download-original actions inside it.
- **Not decided yet / flagged during scoping, needs attention when this is actually built (not before):**
  - **Data model:** likely nullable fields directly on `Entrant` (`deckPhotoOriginalPath`/`deckPhotoPreviewPath`-shaped, matching the PI-33 precedent of adding simple nullable columns for a 1:1 feature) rather than a new table, since it's one photo per entrant with no history requirement — but worth reconsidering if "replace" should keep old versions.
  - **New serving routes** needed (files live on disk, not in Postgres) — and they need to respect PI-27's org public-password-lock the same way every other public data route does, which none of today's routes have had to think about for *file* responses specifically.
  - **Cleanup on delete:** deleting an entrant/pod/tournament/org today relies entirely on DB cascade; a photo file on disk won't get cleaned up by that automatically. This is the app's first feature where a delete route needs an explicit filesystem side-effect, not just a DB cascade.
  - **Backup implications:** self-hosters currently only need to think about backing up Postgres; this adds a second thing (the photo volume) to their backup story. Worth a `docs/deployment.md` note whenever this ships.
  - Accepted file types (JPEG/PNG/HEIC/WebP from phones — the preview generation step needs to handle re-encoding HEIC to something browsers can actually render, since the original stays HEIC for the "download original" action but the preview can't be).
  - Whether an MCP tool is warranted (leaning no, per PI-33's precedent — this is an organizer-at-the-table UI action, not a bulk/scriptable operation).
- [ ] Not started — scoping/interview only.

### PI-113 — Harden outbound webhooks against redirect and DNS-rebinding SSRF (medium severity)
The 2026-09-14 Codex Security scan validated one source-backed finding in `server/src/services/webhooks.ts`. An authenticated organizer may configure and test an arbitrary HTTP(S) webhook. `isSafeWebhookTarget()` resolves and checks the hostname first, but `deliverWebhook()` later calls `fetch()` with the original URL. The actual connection therefore performs a separate DNS resolution and follows redirects by default. A hostname that changes its DNS answer, or an attacker-controlled endpoint returning a 307/308 redirect, can deliver the POST to loopback or link-local services that the current guard explicitly intends to block (CWE-918).

Private RFC1918 destinations remain an intentional product requirement for Home Assistant and similar LAN automation. This item should preserve that behavior and close only the gap between the destination approved by policy and the destination actually contacted.

- [ ] **Block redirect pivots immediately:** set outbound webhook requests to `redirect: "manual"` and treat 3xx responses as failed deliveries. If redirects become a product requirement later, resolve, validate, and pin every hop with a small maximum-hop limit; never delegate redirect handling to the default `fetch()` behavior.
- [ ] **Make DNS validation and connection atomic:** replace the lookup-then-fetch sequence with one shared outbound-request helper that resolves the hostname once, validates every returned address with `isLoopbackOrLinkLocalAddress()`, and binds the actual socket lookup to an approved address while preserving the original hostname for the HTTP `Host` header and TLS SNI/certificate validation. Do not silently fall back to a normal second DNS lookup.
- [ ] **Apply the helper everywhere:** route `sendWebhookEvent`, `sendTestWebhookEvent`, and the operator-level `sendAdminWebhookEvent` through the same pinned-destination path so scheduled, test, and signup deliveries enforce one invariant.
- [ ] **Regression tests:** cover a 307/308 redirect to `127.0.0.1`, `::1`, and `169.254.169.254`; a controlled resolver whose answer changes between validation and connection; multiple DNS answers where any address is denied; and an allowed RFC1918 target to prove the documented LAN use case still works.
- [ ] **Operational verification:** on a real deployment, confirm normal HTTPS webhooks still validate certificates and receive the expected signed body, rejected redirects fail clearly in the Settings test UI, and neither rejection nor DNS failure delays round lifecycle requests beyond the existing five-second ceiling.

**Scan context:** revision `57c344b289621ac412e3cdf7ad88f2ab21af163f`; severity medium, confidence high. The scan was static and did not send exploit traffic. `npm audit` also reported two `mysql2` advisories inherited through Prisma tooling, but the application uses PostgreSQL and no attacker-controlled MySQL runtime path was found, so those advisories are not tracked as an exploitable product finding here.

### PI-114 — Seating chart: dynamic 2-column layout for large pods ⏳ (code-complete 2026-09-14, browser-verify pending)
Tobias flagged (Android Chrome screenshot, a 20-seat pod on `Neuburger Magic Testliga`) that `client/src/components/SeatingChart.tsx`'s two-row layout falls apart once a pod gets large: it always renders `tableCount = Math.ceil(entrantCount / 2)` columns in *one* row, so at 20 entrants that's 10 columns crammed into one screen width — labels overlap/truncate badly, especially on mobile.

**Shipped design — width-driven, not a fixed player-count threshold.** Tobias asked for the flip to be dynamic based on row width rather than a flat ">10 players" cutoff, so it holds up across phone/tablet/desktop sizes:
- The chart's wrapper div is measured live via `ResizeObserver` (`containerRef`/`containerWidth` state in the component).
- `rowModeMinWidth = tableCount * MIN_SEAT_WIDTH_PX + (tableCount - 1) * SEAT_GAP_PX` (`MIN_SEAT_WIDTH_PX = 84`, `SEAT_GAP_PX = 8`, matching the existing `gap-2`) — the width row mode needs to keep every seat readable. Column mode (`isColumnMode`) kicks in once the measured container drops below that. Because the threshold scales with `tableCount`, small pods essentially never flip (their threshold is tiny) and large pods flip even on a moderately wide window — no hardcoded player count anywhere.
- **Column-mode layout:** right column, top-to-bottom = seats `1..tableCount` (same `topRow` array already computed for row mode). Left column, top-to-bottom = `bottomRow` (already ordered `entrantCount..tableCount+1`, unchanged from row mode) — so seat 1 lands top-right, the last seat lands top-left, and the loop still closes correctly: `tableCount`/`tableCount+1` meet at the bottom of the two columns, `1`/`entrantCount` meet at the top. Verified by hand for entrant counts 20 (even), 9 (odd, bye), and 4 (small/even) — see the Node simulation run during implementation.
- The odd-entrant-count empty slot (`emptyBottomSlot`) reuses the exact same "prepend before `bottomRow`" logic in both modes — in column mode that puts the empty chair at the top of the left column, immediately left of seat 1, the natural rotation of "directly below seat 1" in row mode. No new logic needed for this case.
- The caption under the chart switches text to match ("Read top-to-bottom on the right, then bottom-to-top on the left…" in column mode).
- No CSS grid was needed for column mode — cell text is already single-line + `truncate`, so two independent `flex flex-col` columns stay row-aligned without a shared grid.

**Verification status:** `tsc -b` and `eslint`/`prettier` are clean. **Not yet browser-verified** — this sandbox has no Docker/Postgres access (per the standing note at the top of this doc's "New improvements" section) and no browser-automation tooling installed, so the real app couldn't be launched here. The seat-placement math was checked with a standalone Node script (not committed — scratch verification only), not an actual rendered page. Tobias should check on a real running instance:
- [x] Code implemented, typecheck/lint clean.
- [ ] Browser-verify: a small pod (row mode, unchanged), a large pod (~15–20+) at desktop width (row mode, unless very cramped), and the same large pod at phone width (column mode) — confirm seat 1 top-right / last seat top-left, no overlap, and the resize behavior (e.g. rotating a tablet) flips live.
- [ ] Confirm `MIN_SEAT_WIDTH_PX = 84` feels right in practice — it's a tunable constant, not derived from anything; may want adjusting after seeing real names/seat counts on a phone.

### PI-115 — Split a large draft/chaos-draft pod into multiple physical tables ⏳ (code-complete 2026-09-14, browser-verify pending)
Real-world constraint: MTG draft (and chaos draft) physically can't happen at one table past a certain size — boosters get passed around the table, so there's a practical per-table cap. Tobias's ask: once a **draft or chaos-draft** pod has more than 12 entrants, give the TO a choice between one big table (today's behavior) or splitting into multiple physical tables.

**Requirements as given:**
- Trigger: `Pod.format` is `DRAFT` or `CHAOS_DRAFT` (not `SEALED`/`CONSTRUCTED`/`CUSTOM` — splitting is a draft-specific, pack-passing concern) and `entrantCount > 12`.
- Split tables should never go below **6** players. Ideal is **8**; 6/7/9/10 are all fine.
- The system should propose a balanced split, but the TO can rebalance manually — deliberately not a rigid auto-only system, since the right split for a given count is a real-world/venue call, not a pure math one (e.g. 18 could be 10/8 or 6/6/6; 14 could be 7/7 or 8/6 — different groups may prefer different splits for the same count, and physical seating space is part of that decision). **"Rebalance" means adjusting table *sizes* only** (see the clarification below) — it's a setup-time tweak to the shape, not a post-hoc reshuffle of who's at which table.
- **Table layout must be configured *before* seatings are generated**, specifically so the generated seating chart can't bias the split choice — the TO picks table sizes first, blind to who ends up where.

**What's actually there today (checked before writing this up, so the eventual build doesn't have to re-derive it):**
- No "table"/"seating group" concept exists in the schema. `Pod.format` is `enum PodFormat { DRAFT, SEALED, CHAOS_DRAFT, CONSTRUCTED, CUSTOM }` (`server/prisma/schema.prisma:375-381`). The only table-shaped field anywhere is `Match.tableNumber Int` (`schema.prisma:635`), and it's purely positional — both the auto and manual pairing routes assign it as `index + 1` (`server/src/routes/rounds.ts:154-159` and `:250-255`), not a grouping entity.
- **Round-1 pairing has zero format-awareness today.** `generatePairings()` (`server/src/services/pairing.ts`) never reads `pod.format` at all — round 1 is just a shuffle of the whole entrant pool (`pairing.ts:83`) plus a same-weekend soft-avoid (`:69-70`), with no notion of "these N players are grouped." This matters a lot for scoping (see the open question below).
- The seating chart's whole design (PI-51, extended by PI-114) works by **deriving** seat numbers from round 1's pairings after the fact — `client/src/lib/seatings.ts:19-34`'s `computeSeatings` treats the entire pod as one seat-numbering space (`M = ceil(N/2)`, seat `i` pairs with `i + M`), explicitly because "table numbers assigned by the pairing engine are arbitrary" (`seatings.ts:13-18`). `SeatingChart.tsx` then renders one continuous grid sized to that single `M` (`SeatingChart.tsx:36` area, pre-PI-114 line numbers).
- Standings/points (`server/src/services/standings.ts`, `podStats.ts`) and `CardPull` are pod-scoped only and never reference `tableNumber` or any adjacency concept — good news for scoping, since it means splitting into tables doesn't need to touch Swiss pairing for rounds 2+, standings, or Gesamtwertung math at all.
- `PairingsPage.tsx`'s `ManualPairingForm.tsx` (entrant-selection dropdowns for pairings) and the post-publish **swap** action (`POST /rounds/:id/swap`, per `docs/BUILD-LOG.md:339`) exist as manual-override precedents in the app generally, but per the clarification below **neither applies here** — this feature's "manual rebalance" never touches individual entrants, only table-size numbers, so it needs its own much simpler control, not a reuse of either pattern.
- Unrelated but discovered along the way: `PLAN.md:46` and `pairing.ts:32-36` both currently assume "real events are ≤16 entrants" for the whole-pod design. The screenshot that prompted PI-114 already showed a 20-entrant pod in real use, so that assumption is stale independent of this feature — worth a note whenever either item is actually built.

**Decided (Tobias, 2026-09-14): table groupings are physical-seating-only, pairing stays exactly as-is.** Resolves the design fork raised in the first draft of this item — going with the less invasive of the two options:
- Round 1 (and every round's) pairing logic is **untouched**. `generatePairings()` keeps pairing across the whole pod exactly as today, with no awareness of table groups at all — no `pairing.ts` change.
- A table split is purely a physical-seating grouping for the draft/pack-passing phase: which entrants sit at which physical table. It has no effect on who plays whom.
- **Consequence, minimized by design (refined below), not eliminated:** PI-51's original convention — the seating chart derives seat numbers from round 1's match pairings, so your seat's across-the-table neighbor *is* your round 1 opponent — only holds unconditionally for an unsplit (single-table) pod. Once a pod is split, a round 1 pair *can* land at different physical tables (still fine gameplay-wise — decks are already drafted by the time round 1 starts), but the fill algorithm below actively tries to avoid that rather than ignoring it.
- Simplifies the data model: since pairing/standings never need to read table-group membership, storing it is a pure display concern — most likely a nullable per-pod field on `Entrant` (matching the PI-33/PI-62 precedent of simple nullable columns over a new entity), with no corresponding change needed anywhere in `pairing.ts`, `standings.ts`, or the `Match` model.

**Refinement (Tobias, 2026-09-14): fill tables so round-1 pairs land at the same table wherever possible.** Pairing generation itself still stays untouched (previous point stands — this is downstream of it, not a constraint on it) — but the step that assigns *specific entrants* to the pre-configured table slots should use the already-generated round 1 pairing as its input, not assign entrants randomly/blind:
- Round 1 pairing is (barring a bye) a perfect matching — every entrant has exactly one round-1 opponent. Treat each pair as one atomic 2-seat block and bin-pack those blocks into the TO's configured table sizes (a bye, if any, is a 1-seat block). Whenever every table size is even, this achieves **zero** cross-table round 1 pairs — e.g. an 18-entrant pod split 10/8 has 9 pairs to pack: 5 pairs fill the 10-table, 4 fill the 8-table, cleanly, no pair split across tables.
- A cross-table pair only becomes unavoidable when table-size parity doesn't divide evenly among the pair-blocks (e.g. all-odd sizes like 7/7 with no bye to soak the remainder) — in that case exactly one pair has to be split, and that's an acceptable, rare edge case rather than something to over-engineer around.
- This reorders the earlier-assumed sequencing: the table **split shape** (count + sizes) is still configured blind, before round 1 pairing exists, per the original requirement above — the TO shouldn't be biased when choosing 10/8 vs. 6/6/6. But the entrant-to-table **fill** step has to run *after* round 1 pairing is generated (even if not yet revealed to players), since it needs the pairing as input. Practically: TO locks in table shape → system generates round 1 pairing as it does today → system bin-packs pairs into the locked table shape → seating chart and pairings are revealed together, consistent with each other.
**Clarified (Tobias, 2026-09-14): manual "rebalancing" only ever touches table *sizes*, never which entrants land where.** It's a setup-time step, not a post-fill adjustment:
- The TO's only manual lever is the proposed **shape** — how many tables and how big each one is (e.g. system proposes 10/8 for 18 entrants, TO changes it to 6/6/6) — checked against the entrant count and the 6-minimum/no-fixed-maximum rules from the requirements above.
- Once the shape is locked in, the entrant-to-table **fill** is fully determined by the pair-preserving bin-packing algorithm above — the TO has no override over *which* specific entrant ends up at *which* table. No entrant-selection UI, no drag-and-drop, no per-entrant swap.
- This makes the UI much simpler than either existing manual-override pattern cited above: essentially a row of table-size inputs/steppers (add/remove a table, adjust each one's size) with a running total validated against entrant count, offered alongside the system's own proposed shape as a starting point.

**Implemented (2026-09-14):**
- **Schema:** `Entrant.draftTable Int?` (nullable, matching the PI-33/PI-62 precedent), hand-written migration at `server/prisma/migrations/20260914140000_entrant_draft_table/` (sandbox has no Docker/Postgres to run `prisma migrate dev`/`deploy` — Tobias runs that on the real instance).
- **Fill algorithm:** new `server/src/services/tableFill.ts` (`validateTableShape`, `fillTables` — the pair-preserving bin-packing described above), unit-tested in `tableFill.test.ts` (even splits, bye-absorption, forced cross-table split).
- **Round routes (`server/src/routes/rounds.ts`):** both `POST /api/pods/:id/rounds` and `.../rounds/manual` accept an optional `tableSizes`, validated via `resolveTableSplit` (400 `table_split_not_allowed` / `invalid_table_shape` on misuse) and persisted via `persistTableSplit` inside the same transaction as round 1's `Match` rows. `DELETE /api/rounds/:id` clears `draftTable` back to null when round 1 is unpaired, so a re-pair starts the split fresh.
- **Seating (server + client, kept in sync deliberately, same as the existing `computeSeatings` duplication):** `computeSplitSeatings` added alongside `computeSeatings` in both `server/src/services/seatings.ts` and `client/src/lib/seatings.ts`; `SeatAssignment` gained a `table: number | null` field. `client/src/lib/seatings.ts` also gained `groupSeatsByTable`, a shared rendering helper used by both the organizer and public pages.
- **Public API (`server/src/routes/public.ts`):** the seating endpoint now reads `Entrant.draftTable` and switches to `computeSplitSeatings` when the pod is split — still never carries raw pairing data, same privacy posture as before.
- **`SeatingChart.tsx`:** gained an optional `showByeBadge` prop (default `true`, existing call sites unaffected) — split-table rendering passes `false`, since the "last topRow seat = bye" convention only holds for a whole unsplit pod (see the code comment for why a false-positive badge had to be avoided rather than a true-positive one guaranteed — **v1 simplification: the table that actually has the bye entrant isn't specially highlighted**, they just render as a normal seated player).
- **`client/src/lib/tableShape.ts`:** `suggestTableShape`, `validateTableShape`, and the `SPLIT_ELIGIBLE_ABOVE = 12` / `MIN_TABLE_SIZE = 6` / `IDEAL_TABLE_SIZE = 8` constants.
- **`client/src/components/TableShapeForm.tsx`:** the shape-only picker (one big table vs. split, add/remove table rows, live validation) — no entrant-selection UI at all, per the "rebalance is shape-only" decision.
- **`SeatingsPage.tsx`** renders `TableShapeForm` before round 1 exists (only for `DRAFT`/`CHAOS_DRAFT` pods over the threshold), passes the chosen shape into both the auto-generate and manual-pairing paths, and renders one `<SeatingChart>` per table (sorted, labeled "Table N") once a split pod's round 1 exists. **`PublicPodPage.tsx`** mirrors the same per-table rendering from the public seating endpoint.

**Out of scope for this pass (by design, not an oversight):** no pairing-engine changes of any kind; no manual entrant-to-table drag/swap UI; no "this table has the bye" highlighting.

## Project-health backlog (from the 2026-09-06 code audit)

Not feature work — these harden the project itself. None is a live bug at this app's scale (Tobias's own event is 8–10 players); they matter because it's a public OSS project anyone can `docker compose up`, and because a year of AI-assisted sessions has no automated gate catching regressions. The CI / lint / release / hardening keystones (PI-88–91, 93, 94) are shipped and in the build log; what's left below is the still-open remainder plus the dependency and Prisma items.

### PI-92 — Expand CI: migration drift, image build on PRs, boot smoke test ⏳ (migration-drift + lint shipped v0.8.0; image build / smoke test blocked on runner)
PI-88 shipped `.forgejo/workflows/ci.yml` (typecheck + builds + server suite). Three cheap additions catch classes of breakage that suite doesn't touch. Keep it one workflow file; if the image steps drag on the N100 runner, split them into a job that only runs on `pull_request` + pushes to `main`, not every branch.

- [x] **Migration-drift check** — a step in the `check` job. `prisma migrate diff --from-migrations ./prisma/migrations --to-schema-datamodel ./prisma/schema.prisma --shadow-database-url … --exit-code`, run from `server/`. The `--from-migrations` form **does** need a shadow DB (Prisma 6.19 errors without `--shadow-database-url`) — so the step first `CREATE DATABASE lgshadow` on the existing Postgres service via `prisma db execute`, then diffs into it. Verified locally (exit 0 in sync, exit 2 on an un-migrated column) and green on the live runner (task 15, 2026-09-08).
- [x] **Lint** — already added when PI-91 landed (the `Lint + format check` step); left here as a checkbox only.
- [ ] **Docker image build + boot smoke test — blocked, reverted for now.** Built as a separate `image` job (`docker build`, then postgres + the built image + poll `/api/healthz`), but the Forgejo runner executes job steps inside a plain `node:22-bookworm` container with no `docker` CLI and no host socket — `docker: command not found`, task 16 failed. Reverted from `ci.yml` so `main` CI stays green; `docs/development.md` notes the re-add path (runner `config.yml` `container.options` to mount `/var/run/docker.sock`, or a DinD service). The release image is still built + boot-exercised on GitHub for every tag via `docker-publish.yml`, so the only real gap is PR-time.
- [x] **Side finding:** the `check` job had been **failing on `main` since the PI-96/PI-97 commit (v0.7.2)** — `PodList.tsx`/`PodPage.tsx` were committed unformatted, so `format:check` red. Fixed by a `prettier --write` commit alongside v0.8.0; task 15 is the first green `check` since.

### PI-95 — Read-path performance for a 40–60 player event ⏳ (client + query-shape parts shipped v0.8.0; in-process cache + load test still open)
Moving the live instance to a 14 GB box (PI-94) took memory pressure off the table, but the app still recomputes everything from Postgres on every request and the client refetches aggressively. Under ~50 phones at a venue this is a real load pattern — cheap to fix, worth doing before the event.

- [x] **`QueryClient` defaults.** `main.tsx` now sets `staleTime: 30_000` + `refetchOnWindowFocus: false` (was a bare `new QueryClient()` → TanStack's `staleTime: 0` + focus-refetch, so every phone-unlock refetched every query on screen). Realtime Socket.IO invalidation still keeps watched data fresh where it matters. Biggest lever.
- [ ] **In-process cache for `computeGesamtwertung` / `computePodStandings`** — a `Map` keyed by tournament/pod id with a short TTL, busted on the `standings-changed` / pod events. Turns "a result lands → 60 clients refetch → 60 recomputes" into 1 recompute + 60 cache hits. No Redis (fits the stack constraint). **Deferred:** correctness-sensitive (a stale post-result standings is a real bug), and the TTL wants the load test below to tune/verify — not safe to land blind from the dev sandbox.
- [x] **Parallelized `computeGesamtwertung`'s pod loop** — was a serial `for (const pod of pods) { await computePodStandings(pod.id) }` (~50 sequential round-trips for a 10-pod tournament); now `Promise.all` over the pods, then the point-accumulation loop stays sequential for determinism. Confirmed the needed indexes already exist: `Match.roundId` (`@@index([roundId])`), `Round.podId` (`@@unique([podId, roundNumber])` covers it), `Entrant.podId` (`@@index([podId])`).
- [x] ~~**Response compression** — `@fastify/compress` (`global: true`) registered in `index.ts`.~~ **Reverted in v0.8.1 (PI-98).** On the live deploy (Node 22, behind Cloudflare) the plugin returned `200` with `content-length: 0` and an empty body for the larger nested API responses (`/api/tournaments/:id`, and by extension the public tournament/pod pages) — the `vary: accept-encoding` header was there but no payload. Smaller responses (`/api/players`, `/api/tournaments`, gesamtwertung) were fine, so it's size/streaming-triggered. Couldn't reproduce in the Node 20 dev sandbox with the full middleware stack, so root cause is unconfirmed. Behind Cloudflare the plugin bought the live deploy nothing anyway (CF already Brotli's everything); a LAN/non-CF deployer loses on-the-fly compression until this is re-approached with a real load/repro test.
- [ ] **Load test** on the real deploy (k6 / artillery from off-box): ~60 viewer VUs on pod + tournament pages + 2–3 organizer VUs submitting results to drive the broadcast fan-out; watch p95, error rate, `docker stats` mem, `pg_stat_activity`. Include an end-of-round burst (10 results in 5 s).
