### PI-62 — Upload a photo of each entrant's drafted deck (v2 idea, scoped via interview 2026-08-31)
Idea from Tobias: on a pod's standings page, let each entrant have a photo of their drafted deck attached — flagged from the start as "more involved," scoped via an interview before any code. **This would be the app's first-ever user-uploaded file** — every prior "image" in the app (Scryfall card art) is a hotlinked external URL, never something stored by this app itself. `PLAN.md`/`CLAUDE.md` explicitly rule out file uploads for tournament descriptions (PI-31) as a deliberate scope boundary; this is the first place that boundary would be deliberately crossed.
- **Player self-upload now unblocked by PI-52:** PI-52 shipped the player auth surface (`requirePlayerAuth`, `/o/<slug>/player` portal). **Decided sequencing still holds:** ship v1 as **organizer-upload only**, then add a player self-upload path on top of `requirePlayerAuth` — same storage/display, just a second write route.
- **Scope:** any pod format (not draft-only — broader than PI-51's seating chart, which is draft-specific). One photo per entrant (a team pod gets one per team member, not one per team). No upload deadline/window — uploadable, replaceable, or addable anytime during the pod's life, even after it's complete.
- **Storage:** local disk / a new bind-mounted Docker volume, not an external object store — matches the app's existing minimal-moving-parts posture (single Dockerfile + Postgres, no Redis, no other required services). An S3-compatible backend was considered and explicitly declined in favor of this.
- **Keep original quality, but validate + sanitize (decided, refining the initial "resize down?" question):** store the uploaded file at original resolution/quality — but it must be verified as a genuine image (not an arbitrary file wearing a `.jpg` extension) before being accepted. The practical mechanism: decode it through a real image-processing library (e.g. `sharp`/libvips, a **new dependency** this app doesn't have yet) — reject anything that fails to decode as an image at all. Re-saving through that same decode step also strips embedded metadata/EXIF and any polyglot-file payload riding along with the pixel data, which is the standard mitigation for "accept an original-quality photo without accepting arbitrary attacker-controlled bytes." Whether the re-saved copy is byte-identical to the upload or just visually/resolution-identical is an implementation detail to settle when this is actually built, not a scope question.
- **Server-generated preview, not the raw original, for normal viewing:** on upload, also generate and store a smaller preview/thumbnail image (same new `sharp` dependency) — this is what's shown in-app. The full original stays available separately for two explicit actions: **zoom in** (view it at full resolution) and **download original**.
- **Visibility: public, same as the rest of the pod's standings** — no new public/private split. But **hidden by default, revealed on demand**: no thumbnail sits inline in the standings rows at all times. Each entrant gets a small button/link that opens a modal (reusing the shared `Modal` component already built for PI-45's share popup) showing their preview image, with zoom-in and download-original actions inside it.
- **Not decided yet / flagged during scoping, needs attention when this is actually built (not before):**
  - **Data model:** likely nullable fields directly on `Entrant` (`deckPhotoOriginalPath`/`deckPhotoPreviewPath`-shaped, matching the PI-33 precedent of adding simple nullable columns for a 1:1 feature) rather than a new table, since it's one photo per entrant with no history requirement — but worth reconsidering if "replace" should keep old versions.
  - **New serving routes** needed (files live on disk, not in Postgres) — and they need to respect PI-27's org public-password-lock the same way every other public data route does, which none of today's routes have had to think about for *file* responses specifically.
  - **Cleanup on delete:** deleting an entrant/pod/tournament/org today relies entirely on DB cascade; a photo file on disk won't get cleaned up by that automatically. This is the app's first feature where a delete route needs an explicit filesystem side-effect, not just a DB cascade.
  - **Backup implications:** self-hosters currently only need to think about backing up Postgres; this adds a second thing (the photo volume) to their backup story. Worth a `docs/deployment.md` note whenever this ships.
  - Accepted file types (JPEG/PNG/HEIC/WebP from phones — the preview generation step needs to handle re-encoding HEIC to something browsers can actually render, since the original stays HEIC for the "download original" action but the preview can't be).
  - Whether an MCP tool is warranted (leaning no, per PI-33's precedent — this is an organizer-at-the-table UI action, not a bulk/scriptable operation).
- [ ] Not started — scoping/interview only.

### PI-95 — Read-path performance for a 40–60 player event ⏳ (client + query-shape parts shipped v0.8.0; in-process cache + load test still open)
Moving the live instance to a 14 GB box (PI-94) took memory pressure off the table, but the app still recomputes everything from Postgres on every request and the client refetches aggressively. Under ~50 phones at a venue this is a real load pattern — cheap to fix, worth doing before the event.

- [x] **`QueryClient` defaults.** `main.tsx` now sets `staleTime: 30_000` + `refetchOnWindowFocus: false` (was a bare `new QueryClient()` → TanStack's `staleTime: 0` + focus-refetch, so every phone-unlock refetched every query on screen). Realtime Socket.IO invalidation still keeps watched data fresh where it matters. Biggest lever.
- [ ] **In-process cache for `computeGesamtwertung` / `computePodStandings`** — a `Map` keyed by tournament/pod id with a short TTL, busted on the `standings-changed` / pod events. Turns "a result lands → 60 clients refetch → 60 recomputes" into 1 recompute + 60 cache hits. No Redis (fits the stack constraint). **Deferred:** correctness-sensitive (a stale post-result standings is a real bug), and the TTL wants the load test below to tune/verify — not safe to land blind from the dev sandbox.
- [x] **Parallelized `computeGesamtwertung`'s pod loop** — was a serial `for (const pod of pods) { await computePodStandings(pod.id) }` (~50 sequential round-trips for a 10-pod tournament); now `Promise.all` over the pods, then the point-accumulation loop stays sequential for determinism. Confirmed the needed indexes already exist: `Match.roundId` (`@@index([roundId])`), `Round.podId` (`@@unique([podId, roundNumber])` covers it), `Entrant.podId` (`@@index([podId])`).
- [x] ~~**Response compression** — `@fastify/compress` (`global: true`) registered in `index.ts`.~~ **Reverted in v0.8.1 (PI-98).** On the live deploy (Node 22, behind Cloudflare) the plugin returned `200` with `content-length: 0` and an empty body for the larger nested API responses (`/api/tournaments/:id`, and by extension the public tournament/pod pages) — the `vary: accept-encoding` header was there but no payload. Smaller responses (`/api/players`, `/api/tournaments`, gesamtwertung) were fine, so it's size/streaming-triggered. Couldn't reproduce in the Node 20 dev sandbox with the full middleware stack, so root cause is unconfirmed. Behind Cloudflare the plugin bought the live deploy nothing anyway (CF already Brotli's everything); a LAN/non-CF deployer loses on-the-fly compression until this is re-approached with a real load/repro test.
- [ ] **Load test** on the real deploy (k6 / artillery from off-box): ~60 viewer VUs on pod + tournament pages + 2–3 organizer VUs submitting results to drive the broadcast fan-out; watch p95, error rate, `docker stats` mem, `pg_stat_activity`. Include an end-of-round burst (10 results in 5 s).

### PI-102 — v0.9.1 hotfix: v0.9.0 image crash-looped on boot (`nodemailer` not found) ✅ (hotfix v0.9.1; boot-time dependency guard added 2026-09-10)
The v0.9.0 image failed every boot with `ERR_MODULE_NOT_FOUND: Cannot find package 'nodemailer' imported from /app/server/dist/services/mailer.js`. Migrations applied cleanly (all 29, incl. PI-100's) — **the DB was never the problem**; the container just crash-looped after migrating.

**Cause:** the `package-lock.json` committed in v0.9.0 was corrupt. During the PI-101 work, an `npm install` for the deferred `vitest` bump hit an npm 9.2.0 arborist bug (`Cannot read properties of null (reading 'edgesOut')`) and left the lockfile with **`nodemailer` de-hoisted to `server/node_modules/nodemailer`** instead of the root `node_modules/`. It resolved fine locally (Node finds `server/node_modules` walking up from `server/dist`), and `tsc`/`vite build` don't touch runtime resolution — but the `Dockerfile` runtime stage copies **only `/app/node_modules`** (`COPY --from=server-build /app/node_modules node_modules`), so the de-hoisted package never made it into the image. The GHCR build was green because nothing in the build path exercises the runtime `import`.

**Fix (v0.9.1):** regenerated `package-lock.json` from scratch (`rm -rf **/node_modules package-lock.json && npm install && npm ci`) — `nodemailer` + every other server runtime dep now hoist to root, verified with `require.resolve`. The regen also pulled ~119 in-range transitive bumps (rollup 4.62→4.63, @tanstack/react-query 5.102.2→5.102.8, socket.io 4.8.1→4.8.3, etc.) — all within existing `^` ranges, the same set Dependabot's `minor-and-patch` group would land. No source changes, no schema changes. `npm run build` green.
- [x] **Follow-up (hardening) — done 2026-09-10.** The de-hoist hazard is real and standing: bumping `nodemailer` `^10.0.2` → `^10.0.3` and regenerating with npm 10.9.9 de-hoists it into `server/node_modules/` *every time*, even on a clean `rm -rf **/node_modules package-lock.json` regen. New `docker/preflight.cjs` runs from the `entrypoint.sh` (before `migrate deploy`): reads `server/package.json`'s `dependencies` and checks each one has a directory under the image's `/app/node_modules` — exits non-zero, naming the missing packages, if any de-hoisted out of the copied tree. Copied into the runtime image next to `entrypoint.sh`; `docker/**` added to the ESLint `ignores` (deploy helper, outside every tsconfig). Chose the guard over `COPY /app/server/node_modules` (which would drag the dev `typescript` into the runtime image). (`nodemailer` 10.0.3 stays held — see PI-101.)
- [x] **Second regen fallout — CI lint broke from v0.9.1 (found on the PI-104–107 push, run #18/#19).** The v0.9.1 regen also let root `typescript` float **5.9.3 → 6.0.3** (`"peer": true`) — `prisma`'s peer is an unbounded `typescript >=5.1.0`, and the fresh resolve took latest. `typescript-eslint@8.69.0` (peer `>=4.8.4 <6.1.0`, but not actually built for TS 6) then couldn't build a type-checked program for the `mcp` project, so every `mcp/src/*.ts` line lit up `no-unsafe-*` ("Unsafe member access `.env` on a type that cannot be resolved") — 20 errors, lint step red. `npm run build` stayed green because each workspace `tsc` uses its own pinned `typescript@5.9.3`. **Fix:** added `"typescript": "^5.9.3"` to root `overrides` + regenerated the lockfile with npm 10 (`npx npm@10 install --package-lock-only`) — root `typescript` back to 5.9.3, the three de-hoisted workspace copies collapse to one. Minimal diff (−43/+4), matches exactly what v0.9.0 (last green CI) shipped. Remove the override when the toolchain is ready for the deliberate TS 6/7 bump in PI-101's pending-majors batch.
- [x] **Pin removed in the majors batch (T6, `deps/majors-2026-09`).** Root cause of the mcp-only breakage was TS 6+ no longer auto-including `@types/node` — fixed properly with `"types": ["node"]` in `server/tsconfig.json` + `mcp/tsconfig.json`, then TS moved to 7-native for builds with the `@typescript/typescript6` compat for typescript-eslint. The `overrides.typescript` entry is gone.
