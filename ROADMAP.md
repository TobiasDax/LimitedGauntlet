### PI-62 — Upload a photo of each entrant's drafted deck (v2 idea, scoped via interview 2026-08-31)
Idea from Tobias: on a pod's standings page, let each entrant have a photo of their drafted deck attached — flagged from the start as "more involved," scoped via an interview before any code. **This would be the app's first-ever user-uploaded file** — every prior "image" in the app (Scryfall card art) is a hotlinked external URL, never something stored by this app itself. `PLAN.md`/`CLAUDE.md` explicitly rule out file uploads for tournament descriptions (PI-31) as a deliberate scope boundary; this is the first place that boundary would be deliberately crossed.
- **Player self-upload now unblocked by PI-52:** PI-52 shipped the player auth surface (`requirePlayerAuth`, `/o/<slug>/player` portal). **Decided sequencing still holds:** ship v1 as **organizer-upload only**, then add a player self-upload path on top of `requirePlayerAuth` — same storage/display, just a second write route.
- **Scope:** any pod format (not draft-only — broader than PI-51's seating chart, which is draft-specific). One photo per entrant (a team pod gets one per team member, not one per team). No upload deadline/window — uploadable, replaceable, or addable anytime during the pod's life, even after it's complete.
- **Storage:** local disk / a new bind-mounted Docker volume, not an external object store — matches the app's existing minimal-moving-parts posture (single Dockerfile + Postgres, no Redis, no other required services). An S3-compatible backend was considered and explicitly declined in favor of this.
- **Keep original quality, but validate + sanitize (decided, refining the initial "resize down?" question):** store the uploaded file at original resolution/quality — but it must be verified as a genuine image (not an arbitrary file wearing a `.jpg` extension) before being accepted. The practical mechanism: decode it through a real image-processing library (e.g. `sharp`/libvips, a **new dependency** this app doesn't have yet) — reject anything that fails to decode as an image at all. Re-saving through that same decode step also strips embedded metadata/EXIF and any polyglot-file payload riding along with the pixel data, which is the standard mitigation for "accept an original-quality photo without accepting arbitrary attacker-controlled bytes." Whether the re-saved copy is byte-identical to the upload or just visually/resolution-identical is an implementation detail to settle when this is actually built, not a scope question.
- **Server-generated preview, not the raw original, for normal viewing:** on upload, also generate and store a smaller preview/thumbnail image (same new `sharp` dependency) — this is what's shown in-app. The full original stays available separately for two explicit actions: **zoom in** (view it at full resolution) and **download original**.
- **Visibility: public, same as the rest of the pod's standings** — no new public/private split. But **hidden by default, revealed on demand**: no thumbnail sits inline in the standings rows at all times. Each entrant gets a small button/link that opens a modal (reusing the shared `Modal` component already built for PI-45's share popup) showing their preview image, with zoom-in and download-original actions inside it.
- **Not decided yet / flagged during scoping, needs attention when this is actually built (not before):**
  - **Data model:** likely nullable fields directly on `Entrant` (`deckPhotoOriginalPath`/`deckPhotoPreviewPath`-shaped, matching the PI-33 precedent of adding simple nullable columns for a 1:1 feature) rather than a new table, since it's one photo per entrant with no history requirement — but worth reconsidering if "replace" should keep old versions.
  - **New serving routes** needed (files live on disk, not in Postgres) — and they need to respect PI-27's org public-password-lock the same way every other public data route does, which none of today's routes have had to think about for *file* responses specifically.
  - **Cleanup on delete:** deleting an entrant/pod/tournament/org today relies entirely on DB cascade; a photo file on disk won't get cleaned up by that automatically. This is the app's first feature where a delete route needs an explicit filesystem side-effect, not just a DB cascade.
  - **Backup implications:** self-hosters currently only need to think about backing up Postgres; this adds a second thing (the photo volume) to their backup story. Worth a `docs/deployment.md` note whenever this ships.
  - Accepted file types (JPEG/PNG/HEIC/WebP from phones — the preview generation step needs to handle re-encoding HEIC to something browsers can actually render, since the original stays HEIC for the "download original" action but the preview can't be).
  - Whether an MCP tool is warranted (leaning no, per PI-33's precedent — this is an organizer-at-the-table UI action, not a bulk/scriptable operation).
- [ ] Not started — scoping/interview only.

### PI-75 — Notify the operator on new org signup ✅ (code-complete, browser-verify pending)
On a public deployment with `allowSignup` on (e.g. `app.reginerring.com`), nothing tells the person running the instance when a new organization actually signs up.

Audited 2026-09-03: `POST /api/auth/signup` (`server/src/routes/auth.ts:87`) fires no event on success. The existing webhook system (PI-50, `server/src/services/webhooks.ts`) only covers round/pod lifecycle events and is configured per-org, so it can't catch the creation of the org itself. Email infra already exists and is idle for this purpose (`server/src/services/mailer.ts`, nodemailer/SMTP, used today only for invite/account-change mail) — but ruled out below.

**Design, clarified 2026-09-05 (Tobias) — webhook, not email:** the email-alert path is out. Tobias doesn't want SMTP creds configured on a public instance at all — a malicious/spam signup flood is exactly the scenario where having mail-relay credentials sitting on that deployment becomes a liability, not just an inert unused feature. Going with a generic, deployer-configured **operator-level webhook** instead, deliberately receiver-agnostic (not Home-Assistant-specific, even though that's Tobias's own target) so any self-hoster can point it at their own automation platform, Discord, ntfy, whatever. Confirmed the architecture works for a Tailscale-only receiver: webhook delivery is entirely server-side (`deliverWebhook()` is a plain `fetch()` from the Node process itself, not anything the signing-up visitor's browser touches), so it's the *deploy host's* network reachability that matters — a deploy host on the same tailnet as the receiver (e.g. daxvps + a home Home Assistant instance, both on `shire-census`) can reach it exactly like any LAN target. No SSRF-guard changes needed either: `isSafeWebhookTarget()` already only blocks loopback/link-local, not private/CGNAT ranges, specifically because PI-50 was built with "Home Assistant on a self-hoster's own network" as the reference case.
- [x] **Built:** `ADMIN_WEBHOOK_URL` + `ADMIN_WEBHOOK_SECRET`, same "inert unless set" posture as `TRACKING_*`/`SMTP_*`/`TRUSTED_PROXIES`. `parseAdminWebhookConfig()` (`services/webhooks.ts`, same "pure, throw clearly on malformed config" shape as `parseTrustedProxies`/`parseTrackingConfig`) validates a well-formed `http://`/`https://` URL (deliberately not https-only, unlike PI-85's tracking script — the realistic target here is a plain-http LAN/Tailscale receiver, same allowance the per-org `webhookUrl` Zod schema in `settings.ts` already gives organizers) and a secret of at least 16 chars. `config.ts` exposes `config.adminWebhook: AdminWebhookConfig | null`.
- [x] **Built:** `WebhookEventType` widened with `organization.created`; `sendAdminWebhookEvent()` reuses `deliverWebhook`/`isSafeWebhookTarget` as-is (takes the config as a parameter rather than importing `config.ts`, avoiding a `config.ts` ↔ `webhooks.ts` circular import) — never throws, same posture as `sendWebhookEvent`. A small `notifyAdminOfNewOrg()` helper in `auth.ts` wraps the `fireAndForget` + no-op-when-unset check once, called from **both** places a brand-new org actually gets created — the plain signup route and the OIDC-bootstrapped registration route — but not accept-invite, which joins an *existing* org already announced when it was first created.
- [x] **Payload:** org name/slug + creator's email, no standings/match-shaped data to reuse from the PI-50 payload builders here — a much simpler shape.
- [x] **Tests:** 6 new cases in `webhooks.test.ts` (inert-by-default, valid config incl. `http://`, malformed/non-http(s) URL rejection, missing/too-short secret rejection, signed delivery incl. verifying the HMAC header, never-throws on an unreachable-but-safe target, skips an unsafe loopback/link-local target). Full server suite 134/134. `tsc -b` clean.
- [x] **Docs:** `.env.example`, both `docker-compose*.yml`, `docs/deployment.md` §11, `README.md`'s env-var reference all cover the two vars, matching the SMTP/tracking/webhooks treatment.
- [ ] **Follow-up (observability, from a live-debug session 2026-09-05):** Tobias's first setup had two URLs accidentally concatenated into `ADMIN_WEBHOOK_URL` (`http://ha/api/webhook/` + a full second URL pasted as the "id"). `new URL()` accepts it (`://` is legal in a path), so it passed startup validation and then silently 404'd against HA forever, and the failure log (`Admin webhook delivery failed { ok: false, status: 404 }`) didn't include the URL, so diagnosing it needed `docker compose exec app printenv`. Two cheap fixes:
  - `parseAdminWebhookConfig()` — reject a URL whose *path* contains `://` (a second scheme in the path is essentially always a paste error); fail at startup with a clear message.
  - `sendAdminWebhookEvent()`'s failure `console.warn` — include the target URL (or at least origin + path) so a mangled URL shows up directly in `docker compose logs`.

### PI-77 — Sink finished pods to the bottom of a tournament's pod list, ordered by completion ✅ (code-complete, browser-verify pending)
Idea from Tobias, scope corrected 2026-09-04 (originally drafted against the tournament dashboard — it's actually about the **pod list within a tournament**, alongside PI-76's reorder work): as a tournament's pod list grows, finished pods should settle below the still-running/upcoming ones instead of staying mixed in at their creation-order position.

**Decisions (Tobias, 2026-09-04):**
- **No hide toggle, no separate tab.** One flat list, partitioned: unfinished pods first, then a visual spacer + a small "Finished" headline, then finished pods. Nothing is ever hidden.
- **Unfinished pods:** ordered by PI-76's manual reorder (i.e. `sequenceOrder`, whatever PI-76 lands it as).
- **Finished pods:** ordered by **completion order** — the first pod that finished sits at the top of the finished group, the most recently finished at the bottom.
- **Historical/imported data:** fine for completion order to be set manually/at import time rather than reconstructed from real timestamps — not a blocker.

Audited 2026-09-04: "finished" already has a derived definition — `podProgressStatus()` (`usePods.ts`, PI-58) says "Finished" once the pod's last configured round (`roundNumber === roundCount`) is `COMPLETED`, computed fresh from real `Round` data every render (not a stored flag). That's the right signal to reuse here too, rather than inventing a second "finished" concept — the raw manual `Pod.status` enum stays what it's always been (mostly untouched except by `import-legacy.ts`) and doesn't need to become load-bearing for this.
- [ ] **Completion order needs a new stored timestamp — this is the one real gap.** Nothing today records *when* a pod finished: there's no `updatedAt` anywhere in `schema.prisma`, and `Round` stores no completion timestamp (only `status`). Add `Pod.completedAt DateTime?`.
- [ ] **Reuse, don't duplicate, the completion-detection logic:** `syncPodTokenAwards` (`services/tokens.ts:52`) already computes the exact boundary needed (`finalRoundDone = pod.rounds.some(r => r.roundNumber === pod.roundCount && r.status === "COMPLETED")`) and is already hooked into every place that can flip it — `rounds.ts` ×3, `playerAccounts.ts`, pod entrant add/remove/drop/undrop, pod update, tournament update, the settings toggle. Set `Pod.completedAt = now()` the moment that flips true, clear it back to `null` if it flips false again (e.g. `roundCount` raised after completion re-opens the pod, per the "un-completes the pod" comment at `rounds.ts:270`) — piggyback on this existing sync pass rather than adding a second parallel check.
- [ ] **`import-legacy.ts`** already sets `Pod.status = "COMPLETED"` for historical pods (the one place that field is set today) — extend it to also stamp `completedAt` at import time (e.g. derived from the pod's `date` field or `sequenceOrder`) so a full historical import gets a sensible completion order without needing real historical timestamps, matching Tobias's "no real problem" framing.
- [ ] **Frontend:** partition `tournament.pods` into unfinished/finished; unfinished keeps its existing order, finished sorts by `completedAt` ascending. Render the spacer + "Finished" headline between the two groups. Apply to both `TournamentPage.tsx` (authed) and `PublicTournamentPage.tsx` (public).
- [ ] **Interacts with PI-76** (reorder applies within the unfinished group only) **and PI-81** (Scheduled/On-demand tabs) — if both ship, this finished/unfinished partition applies *inside* each of PI-81's two tabs, not across them.
- [x] **Built:** `Pod.completedAt DateTime?` (migration `20260905120000_pod_list_reorder_lifecycle_fields`, bundled with every other PI-76..84 field below). Stamped/cleared in `syncPodTokenAwards` (`tokens.ts`) — moved ahead of its `tokensEnabled` early-return so this tracks purely off `finalRoundDone`, independent of tokens being on; stamped once (not refreshed on every later sync), cleared back to `null` if `roundCount` is raised and re-opens the pod. `import-legacy.ts` derives a deterministic per-pod `completedAt` from `sequenceOrder` (no real per-pod timestamp exists in legacy sources). `PodList.tsx` (new, shared by `TournamentPage` and `PublicTournamentPage`) partitions unfinished/finished exactly as specified — spacer + "Finished" headline, finished sorted by completion order — and **already implements the PI-81 interaction**: partitioning happens inside each Scheduled/On-demand tab.
- [x] **Tests:** 3 new cases in `tokens.test.ts` covering stamp-on-finish (tokens-disabled org too), no-re-stamp-on-repeat-sync + clear-on-un-complete, and (PI-84) canceled pods still get `completedAt` tracked even though they're withheld from token awards. Full server suite 112/112.
- [x] **Bug found on first live browser-verify (2026-09-05), fixed:** the `20260905120000` migration added `completedAt`/`canceledAt` with no backfill, so on any database with pre-existing pods (the live demo included, not a fresh install) every already-finished pod kept `completedAt = NULL` forever — nothing re-touches it, since `syncPodTokenAwards` only fires on *later* completion-changing actions. `partitionFinished` (`lib/podOrder.ts`) reads that raw column, not `podProgressStatus`'s rounds-derived label, so those pods showed "Finished" on their row but never sank into the finished group — and, staying bucketed as "unfinished", wrongly kept their reorder arrows too. Symptom Tobias hit: a brand-new Setup pod rendered *below* five already-finished pods, arrows on every row, no visible "Finished" divider. Fixed with a follow-up data migration (`20260905140000_backfill_pod_completed_at`) that stamps `completedAt` (from each pod's `createdAt`, no real completion timestamp exists for pre-migration data) for every existing pod whose last configured round is already `COMPLETED`. Re-verify live after this migration runs.
- [ ] Browser-verified.

### PI-78 — Drop a player from the Pairings screen, including mid-round via match-result entry ✅ (code-complete, browser-verify pending)

The organizer spends the event on the **Pairings** tab, and a player often drops mid-match (concedes, has to leave), not neatly between rounds. Put the control where the work happens, and let it actually fire mid-round.

**Clarified 2026-09-04 (Tobias) — two changes, scope corrected:**
1. **Players must be droppable while a round is active.** When they drop, the result of the match they were playing still gets recorded (whatever was actually played), and the organizer picks who dropped from a dropdown alongside that result entry: **No one dropped** (default) / **Player 1 dropped** / **Player 2 dropped** / **Both dropped**.
2. **Scope is the Pairings page only.** (Retracts the earlier draft's option (b), which had proposed folding a standings/match-points panel into this page — that was a mix-up, not the ask. PI-78 is the drop control, nothing about standings display.)

Round completion already requires every non-bye match to have a non-`PENDING` result (`results_missing` check, `rounds.ts:378`), so "record the last match's result, then mark the drop" is already the natural sequence the round-completion flow expects.
- [ ] **New in-match drop path:** extend `resultSchema` with an optional `dropped: z.enum(["NONE", "A", "B", "BOTH"]).default("NONE")`. - [ ] **This is additive, not a replacement** for the existing standalone `POST /api/entrants/:id/{drop,undrop}` (PI-63) — that stays gated to between-rounds for the "player leaves before their next match even starts" case (no match to attach the drop to). The two paths cover different moments: in-match dropdown for "dropped during this round," standalone control for "dropped before the next round starts."

Also extract `EntrantDropControl` onto `PairingsPage` for the between-rounds case (the original ask), reusing it verbatim from `PodPage.tsx` (same `canModifyRoster` gate, same badge/error copy) — so both drop affordances end up on this one screen.
- [ ] Verify no other logic assumes a drop can only happen between rounds — check `podStats.ts`/`weekendHistory.ts`/`tokens.ts`'s standings-bonus recompute for any implicit "round must be COMPLETED" assumption tied to `droppedAfterRound` (not just the route-level 400 removed here).
- [x] **Built:** `resultSchema` (`rounds.ts`) gained `dropped: z.enum(["NONE","A","B","BOTH"]).default("NONE")` exactly as scoped; `PATCH /api/matches/:id/result` now does the match-result update and (when non-`NONE`) the matching `Entrant.droppedAfterRound = round.roundNumber` write(s) in one `$transaction`. `EntrantDropControl` extracted out of `PodPage.tsx` into `client/src/components/EntrantDropControl.tsx` verbatim (same `canModifyRoster` gate/copy), reused by both `PodPage` and a new between-rounds roster list on `PairingsPage` (right above the "Pair round N" action, gated on the same between-rounds condition). `ResultEntry` gained the 4-option dropdown, labeled with real entrant names via a `droppedOptions()` helper — shown both on a fresh result entry and when editing an already-reported one.

### PI-79 — Seating chart for SEALED events too ✅ (code-complete, browser-verify pending)

But a SEALED event still seats everyone at a table, and the group wants an assigned seating for it as well (matches how their old Outline docs handled sealed).

### PI-85 — Deployer-configured web analytics (Umami first), via env vars only ✅ (code-complete, browser-verify pending)
Idea from Tobias: he's standing up his own Umami instance and wants its tracking snippet on every page this app serves — but since other self-hosters would want *their own* tracking (or none), the provider + credentials must come from env config, never a hardcoded/personal default. Explicit requirements: (1) provider-abstracted so a second analytics provider can be added later without redesigning the mechanism, even though only Umami is supported now; (2) hard-gated against arbitrary code injection — an env var must never become a way to run attacker-controlled script on every page.

**Design, clarified 2026-09-04 (Tobias + a resolved open question):**
- **Three env vars, not two** — auditing Umami's actual embed snippet surfaced a gap in the original two-variable plan: a self-hosted Umami needs both a **script host** (`https://<your-umami-domain>/script.js` — different per deployer, including Tobias's own) and a **website ID** (a UUID). Resolved: `TRACKING_PROVIDER` (enum, `"umami"` only for now), `TRACKING_SCRIPT_URL` (the deployer's own script host), `TRACKING_CODE` (the provider-specific id/token — Umami's website UUID). Unset `TRACKING_PROVIDER` = feature fully inert, same "off by default" posture as SMTP/OIDC/webhooks/`LEGAL_LINK_URL`.
- **Anti-injection gate (the hard requirement):** never trust these values as raw HTML/script. Validate strictly at startup — `TRACKING_PROVIDER` through a Zod enum (`z.enum(["umami"])`, widened as providers are added, invalid value = refuse to start or log-and-disable, matching `parseTrustedProxies`'s "throw clearly on malformed config" precedent from PI-48); `TRACKING_SCRIPT_URL` must parse as a well-formed `https://` URL (reject `javascript:`/`data:`/anything non-http); `TRACKING_CODE` validated against a **per-provider pattern** (e.g. Umami's website id is a UUID — reject anything else). The provider registry (below) is the only thing that ever turns these validated values into a script tag's `src`/`data-*` attributes — never raw env-to-HTML interpolation anywhere.
- **CSP conflict, must be fixed together:** `server/src/index.ts`'s Helmet CSP locks `scriptSrc`/`connectSrc` to `["'self'"]` (added under PI-46/48's security hardening). An external Umami script would be **silently blocked** by this (CSP failures are invisible in the UI) unless the configured script host's origin is added to both directives at server startup — parsed from the validated `TRACKING_SCRIPT_URL`, same "parse deployer env into runtime CSP/config" shape as `TRUSTED_PROXIES`.

### PI-86 — One person, multiple organizations (organizer + player), with an in-app switcher ✅ (merged; browser-verified on the demo — live rollout needs a DB backup first, see the deployment note below)

**Problem (Tobias, 2026-09-05):** an organizer account is permanently bound to exactly one org. If someone who's already an organizer of org A is invited to org B, neither path works: the SSO login (`linkOrProvisionFromSso`, `sso.ts:266`) matches their existing account by subject and logs them straight back into org A, silently ignoring the org-B invite; the password `POST /api/auth/accept-invite` tries to `create` a second `OrganizerAccount` with the same email and hits the `email @unique` constraint. Same limitation for players (PI-52) — and worse, since players have no shared identity at all (each `Player` row carries its own `passwordHash`). Tobias wants one login that can belong to several orgs and switch between them.

**Current model — where the "one org" assumption lives:**
- `OrganizerAccount` conflates **identity** (`email @unique`, `passwordHash`, `oidcSubject @unique`, `name`, `authVersion`) with **membership** (`orgId` FK, `onDelete: Cascade`). Every org-scoped route filters by `request.organizer.orgId`, set once in `middleware.ts`'s `setOrganizer` from `account.orgId`.
- `ApiToken.organizerId` → the token acts as that organizer in their single org. No org on the token itself.
- `Player.orgId` + `@@unique([orgId, email])` — the *same email can already be a different `Player` row per org*, but there's no `PlayerIdentity`, so it's a separate password + separate login per org, no switching. Player session stores one `playerId`.
- `EmailChangeRequest` / `OidcSubjectRelinkRequest` are keyed by `organizerId` (the identity) — unaffected by a split.
- Session (`auth/types.ts`) stores `organizerId` + `authVersion` (and `playerId` + `playerAuthVersion`). No concept of an "active org".

**Decisions (Tobias, 2026-09-05 — all open points resolved):**
- **Both sides in one pass** — organizer split *and* the player-identity split ship together, not phased.
- **Naming stays close to today:** `OrganizerAccount` keeps its name (just loses `orgId`); new `OrganizerMembership` is the join row. On the player side, `Player` stays the per-org roster entry and a new `PlayerIdentity` is the login it links to. (Accepted the slight `OrganizerAccount` vs `PlayerIdentity` asymmetry to avoid a repo-wide rename landing in the same change.)
- **Login lands on the last-used org** — `lastActiveOrgId` stored on the account (and on `PlayerIdentity`); first-ever login with no history falls back to the only / oldest membership.
- **Removed from your active org mid-session → bounce to the org chooser** on the next request (not a silent fallback, not a logout). Same chooser a membership-less account sees.
- **Leaving your last org keeps a membership-less account** — it can log in and lands on the chooser ("you're not in any organization: accept an invite, or create one"). The org's `ApiToken`s / webhooks / etc. are deleted with the org as usual.
- **Roles stay flat** — no per-membership roles, no owner marker. Every member of an org has equal power, exactly as PI-34 shipped it.
- **An invite is bound to its addressed identity.** Opening an invite for `bob@y` while logged in as `alice@x` is blocked with a clear message ("log out and accept as bob@y, or via SSO with that identity") — the invite never attaches to whichever account happens to hold the link.
- **Players switch via an explicit switcher in the player portal**, mirroring the organizer top-bar dropdown; the `/o/<slug>/player` URL follows the switcher's choice.

**Shape:**
- **Split membership out of the identity.** `OrganizerMembership { accountId, orgId, lastActiveAt?, createdAt, @@unique([accountId, orgId]) }`. `OrganizerAccount` loses `orgId`; `Organization.organizers` → `memberships`. Everything downstream still filters by a single `orgId` — only `middleware.ts` changes: resolve the active org from the session, verify a membership exists, set `request.organizer.orgId`. Every other route's contract is unchanged.
- **Active org in the session.** Add `activeOrgId` (+ `activePlayerOrgId` for the player session). Middleware uses it when the membership still exists; otherwise → 302 to the org chooser (`GET /api/auth/me` returns a flag the frontend routes on). `lastActiveOrgId` on `OrganizerAccount` / `PlayerIdentity` records where to resume. New `GET /api/auth/organizations` (membership list) + `POST /api/auth/switch-org` (validate membership, set `activeOrgId`, no `authVersion` bump). `/api/auth/me` gains the membership list + the active id.

### PI-89 — Guard the pairing search against pathological pod sizes ✅ (v0.8.0)
`generatePairings` (`server/src/services/pairing.ts`) solves an **exact minimum-cost perfect matching** via recursive branch-and-bound (`solvePool` → `bestMatching`). The `candidate.cost >= best.cost` prune keeps it fast at real pod sizes (PLAN.md's stated ceiling is ≤16 entrants), but the worst case is **exponential**: a large pod where the cost function produces many near-equal options — dense repeat-elsewhere-this-weekend history (round 1) plus everyone bunched on similar points — defeats the prune, and an odd pool multiplies it by re-solving for each bye candidate in `byeOrder`. A 30-plus-entrant pod with adversarial history could pin the event loop for a very long time. Not a live bug (real events are ~10 players) — but "someone makes a 40-person pod" shouldn't be able to wedge a shared instance.

- [x] **Both guards, belt-and-braces.** `EXACT_MATCHING_POOL_LIMIT = 18` — above it, skip the exact solver entirely. `MATCHING_CALL_BUDGET = 300_000` — a recursion-call counter threaded through `bestMatching` (now `solveExact`); exceeding it throws `MatchingBudgetExceeded`, which unwinds out of the bye loop and restarts the whole pairing greedy (so an exact bye choice never gets mixed with a greedy remainder). Numbers picked from a timing sweep: realistic costs stay <30 ms to n=18 and the exact solve blows past 300 k calls around n≥20; a repeat-dense n=16 round 1 (near-equal costs, the real pathology) hit ~760 ms / ~5 M calls unguarded and now bails at ~30–40 ms.
- [x] **Greedy score-group fallback** (`solveGreedy`): walk the pool in order (points desc, or the round-1 shuffle), pair each unpaired entrant with the nearest later entrant they haven't faced in this pod; honours the within-pod hard-avoid (skips `Infinity`-cost partners), only accepts a repeat when a player has already faced everyone left below them (same situation the exact solve would return `null` on). Drops the global optimum and the round-1 soft-avoid weighting — standard Swiss.
- [x] **Surfaced** via a `console.warn` (`[pairing] pod <id> round <n>: N active entrants — used greedy score-group pairing…`) whenever the fallback runs. No change to the pairing response shape — `suggestion` never reaches the client, only the created `Round`/`Match` rows do.
- [x] **Test:** `pairing.test.ts` gains a 32-entrant / 4-round pod — asserts each round generates in <1 s, 16 pairs, all 32 covered, and no repeat opponent across all four rounds (greedy still honours the hard-avoid). Server suite 139/139.

### PI-93 — Tag-triggered GHCR build + release (kept on GitHub Actions) ✅ (2026-09-08, v0.7.0 — first release on the new path)
